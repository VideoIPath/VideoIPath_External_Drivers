# SPEC-23 frames and this example's behavior

These are complete JSON WebSocket frames using the later SPEC-23 v1 baseline.
They are teaching examples derived from the documented contract and current
source, not captures accepted by a VideoIPath release. No live instance or
release-specific decoder/schema fixture has been supplied. The simulator's Unix
protocol is a separate API described in [SIMULATOR.md](SIMULATOR.md).

The executable has no command for injecting these SPEC frames. A backend or a
local test harness sends them to the driver. [SCENARIOS.md](SCENARIOS.md) contains
the actual local CLI and explains what can be exercised without VideoIPath.

## Transport and envelope

The driver initiates `wss://HOST/x-driver/v1?node_id=UUID`, using an
`Authorization: Bearer …` opening header. Configure the URL without the query;
the application adds the provisioned UUID. TLS/hostname verification is enabled.
The SPEC opening result is HTTP 101, with 401 for invalid authentication.
Token revocation and duplicate-node takeover are backend behaviors requiring
target verification; a local lock prevents duplicates only on a shared host mount.

Requests use integer IDs; responses preserve the ID and type except for `error`.
The handler DTO uses `i128` to preserve both signed and unsigned 64-bit JSON
integers without narrowing. Send monotonically increasing nonnegative IDs; the
driver does not enforce monotonicity or duplicate-ID reuse.
Async events use `message_id: null`. Unknown object fields are ignored; required
known fields and supported enum values still require validation. This is a
derived implementation, not a published formal JSON Schema.

Keepalive is echoed as the original text, including extra fields:

```json
{"message_id":1,"message_type":"keepalive","data":null,"future_field":42}
```

The identical frame is the response. No autonomous WebSocket ping loop is started.
Loss of target health or 60 seconds without backend application traffic closes
the session. An incoming `error`, including an async error, is logged without its
payload and receives no response. An unsupported request with a usable ID gets:

```json
{"message_id":2,"message_type":"unrecognized_operation","data":null}
```

```json
{"message_id":2,"message_type":"error","data":"Unsupported capability"}
```

Malformed JSON or an unusable request ID closes the session. The session handles
malformed envelope errors separately, so their fixed wording can differ from
capability errors. Never invent a request ID for an uncorrelatable frame.

## Structure and identity

```json
{"message_id":3,"message_type":"get_structure","data":null}
```

The response uses ID 3, type `get_structure` and the complete object generated by
[`Registry::new()`](../src/registry.rs). It contains two modules, root/module/port
definitions, main/spare interfaces, an auxiliary interface and one `rx-tx` resource
link. `tx-1` and `rx-1` have the device-defined `format_id: "raw-video"`; this is
resource metadata, not a promise of raw-video SDP support. `rx-audio` separately
advertises Audio topology and the PCM SDP subset. The auxiliary module's display
label is `Auxiliary Console 42`. Structure definitions describe capabilities, not current values. See the
[fixture inventory](SCENARIOS.md#the-current-fixture) for its stable IDs.

| Location | Wire value | Example local ID |
| --- | --- | --- |
| Device | `null` | `enabled` |
| Module | `{"module_id":"module-1","port_location":null}` | `enabled` |
| Sender | `{"module_id":"module-1","port_location":{"type":"sender","id":"tx-1"}}` | `enabled` |
| Receiver | Same module with `{"type":"receiver","id":"rx-1"}` | `enabled` |
| Generic component | Same module with `{"type":"generic","id":"fan-1"}` | `enabled` |
| Network interface | Same module with `{"type":"network_interface","id":"net-main"}` | `enabled` |

`(location, local_id)` is the identity. These repeated `enabled` IDs are independent.
The parameter named `enabled` is a modeled parameter, not an alias for IPT enable
or disable. Module/port labels and IDs remain stable across simulator restarts.
`DRIVER_CONFIGURATION_ORDER` selects `senders_first` (default), `receivers_first`
or `all` at startup. Both directions are accepted in an `all` batch, but device
calls remain sequential; this is not atomic or parallel apply.

## Dynamic values

Starting from a fresh simulator:

```json
{"message_id":10,"message_type":"get_dynamic_values","data":{"location":null,"ids":["level","audio_gain","missing"]}}
```

```json
{"message_id":10,"message_type":"get_dynamic_values","data":{"audio_gain":0.0,"level":50}}
```

Unknown requested IDs are omitted. With `ids` absent or null, this example returns
all **advertised readable** values at the location. Hidden scratch IDs require
explicit selection. An empty list selects nothing and returns `{}` after a fresh
snapshot. This empty-list policy needs target confirmation. Explicitly selecting
write-only `trigger` fails the whole read with `Write-only parameter`; ordinary
all-values reads omit it. A device read failure is a correlated top-level error,
not a stale success or an invented per-ID read-error object.

A partial write processes valid entries despite other per-ID failures:

```json
{"message_id":11,"message_type":"set_dynamic_values","data":{"location":null,"values":{"level":60,"audio_gain":2.5,"temperature":30,"missing":1}}}
```

```json
{"message_id":11,"message_type":"set_dynamic_values","data":{"missing":"Unknown parameter","temperature":"Read-only parameter"}}
```

Then, after response delivery:

```json
{"message_id":null,"message_type":"async_values_changed","data":{"location":null,"values":{"audio_gain":2.5,"level":60}}}
```

Successful writes return `data: {}`. The failure map is direct: there is no
`failures` wrapper. Repeating the same values generates no causal change event.
`level: true` fails with `Invalid value type`; `level: 101` and `audio_gain: 0.25`
fail with `Out of range`. Numeric values must be finite; integer-only parameters
require JSON integers, rejecting `60.0` as well as fractional values. String
`mode` accepts only `standby` or `active`. Root `signal_present` is a read-only
GPI boolean initially true; root `mute` is a read/write, GPO-only boolean initially
false. Independent control changes to the signal produce normal async observations;
a backend write receives `Read-only parameter`.

A scoped write leaves root `enabled` unchanged:

```json
{"message_id":12,"message_type":"set_dynamic_values","data":{"location":{"module_id":"module-1","port_location":{"type":"sender","id":"tx-1"}},"values":{"enabled":false}}}
```

```json
{"message_id":12,"message_type":"set_dynamic_values","data":{}}
```

```json
{"message_id":null,"message_type":"async_values_changed","data":{"location":{"module_id":"module-1","port_location":{"type":"sender","id":"tx-1"}},"values":{"enabled":false}}}
```

Write-only `trigger` counts every accepted invocation, even repeated boolean
inputs. It has no readable state or fabricated value-change event and is never
automatically replayed. Unadvertised `sim.user.1` and `sim.user.2` accept integers
0–100; arbitrary URLs, files and OIDs are not resolved.

Backend mutations hold an exclusive session lane through their response and
causal-event delivery. Independent events retain private simulator revisions
until dispatch, where each value is checked against its own confirmed-write
revision floor. A stale event or conflict with the mutation lane closes the
session for resynchronization. `_driver_revision` is removed before serialization
and is **not a SPEC field**. This detects uncertainty; it does not reconstruct
event history or guarantee exactly-once delivery.

## Alarms

Fresh simulator poll:

```json
{"message_id":20,"message_type":"alarms","data":null}
```

```json
{"message_id":20,"message_type":"alarms","data":[]}
```

After the scoped alarm command in [SCENARIOS.md](SCENARIOS.md#alarms), the driver
can forward this independent event and return this authoritative poll:

```json
{"message_id":null,"message_type":"async_alarm","data":{"id":"Link Down","location":{"module_id":"module-1","port_location":{"type":"network_interface","id":"net-main"}},"details":"Modeled carrier loss","severity":"major","service_affecting":true}}
```

```json
{"message_id":21,"message_type":"alarms","data":null}
```

```json
{"message_id":21,"message_type":"alarms","data":[{"id":"Link Down","location":{"module_id":"module-1","port_location":{"type":"network_interface","id":"net-main"}},"details":"Modeled carrier loss","severity":"major","service_affecting":true}]}
```

An alarm is identified by `(location, id)`. Updating its details or severity
refreshes the same alarm. Valid severities are `notification`, `minor`, `warning`,
`major`, `critical`; omitted `service_affecting` defaults to true. False is valid.
Missing alarms in a subsequent successful full poll are cleared; `[]` clears all.
The application rejects invalid or duplicate alarm identities rather than sending
an ambiguous snapshot. Simulator admission also accounts for escaped JSON size:
the entire snapshot and reply envelope must fit the private transport frame.
Capacity rejection leaves the prior alarm state and revision intact.

```json
{"message_id":null,"message_type":"async_alarm_cleared","data":{"location":{"module_id":"module-1","port_location":{"type":"network_interface","id":"net-main"}},"id":"Link Down"}}
```

```json
{"message_id":null,"message_type":"async_poll_alarms","data":null}
```

Neither event expects a response. The SPEC schedules a triggered poll in about a
second unless an existing poll is sooner; this driver does not run that backend
scheduler. `poll-alarms` requests a poll; it does not itself create or clear alarms.

## IPT configuration and SDP

This modeled sender is useful for readback, supported SDP and drift exercises.
It explicitly selects H.264 and dynamic payload 111, which the sender SDP subset
can describe. The fixture still produces no media.

```json
{"message_id":30,"message_type":"set_ipt_configurations","data":{"module_id":"module-1","sender_configs":[{"id":"tx-1","sub_index":null,"transceiver_type":"sender","enabled_config":{"main_ip_destination":{"udp_port":5004,"address":"239.1.1.1","vlan":null,"network_interface":{"module_id":"module-1","port_id":"net-main"}},"spare_ip_destination":null,"format_info":{"video_codec":{"codec":"H.264","entropy_encoding":"CABAC","gop_struct":"IPB","gop_size":12},"attributes":{"rtp_payload_type":111}},"fec":null,"streaming":{},"resource_partner":null,"srt":null}}],"receiver_configs":[]}}
```

```json
{"message_id":30,"message_type":"set_ipt_configurations","data":{"sender_config_errors":[],"receiver_config_errors":[]}}
```

```json
{"message_id":31,"message_type":"get_sender_sdp","data":{"module_id":"module-1","port_id":"tx-1"}}
```

```json
{"message_id":31,"message_type":"get_sender_sdp","data":"v=0\r\no=- 1 1 IN IP4 127.0.0.1\r\ns=Modeled RTP session\r\nt=0 0\r\nm=video 5004 RTP/AVP 111\r\nc=IN IP4 239.1.1.1/64\r\na=rtpmap:111 H264/90000\r\n"}
```

Sender SDP supports single-stream H.264 or H.265 video RTP, using `H264` or `H265`
and the explicit payload 96–127 from observed state. IPv4 multicast includes the
streaming TTL, defaulting to 64. Missing/unsupported codecs or payloads, other
format attributes, audio pairs, spare streams, SRT, FEC, receiver-source fields
and supplied SDP overrides return `Unsupported capability`; no raw-video fallback
or DUP group is invented. A configuration can be valid modeled IPT state while
its SDP representation is unsupported.

Only `tx-1` advertises sender SDP. An unsupported sender produces `Unsupported
capability`; an unknown port produces `Unknown parameter or resource`. Disabled
`tx-1` returns null. There is no separately modeled pending-generation state, even
though the SPEC allows null while generation is pending.

Receiver application supports one RTP/AVP section: H264/H265/MP2T video on `rx-1`, or
L16/L24 PCM audio on `rx-audio`. This independent MP2T example deliberately uses
a different encoding from the sender example above; they are not a matched
end-to-end media path:

```json
{"message_id":32,"message_type":"set_ipt_configurations","data":{"module_id":"module-1","sender_configs":[],"receiver_configs":[{"id":"rx-1","sub_index":null,"transceiver_type":"receiver","enabled_config":{"main_ip_source":{"udp_port":5004,"source_address":"192.0.2.20","destination_address":"239.1.1.1","vlan":null,"network_interface":{"module_id":"module-1","port_id":"net-main"}},"spare_ip_source":null,"format_attributes":{"rtp_payload_type":33},"fec_enabled":false,"srt":null,"sdp":"v=0\r\no=- 1 1 IN IP4 192.0.2.20\r\ns=Modeled receive session\r\nt=0 0\r\nm=video 5004 RTP/AVP 33\r\nc=IN IP4 239.1.1.1\r\na=rtpmap:33 MP2T/90000\r\n","source_meta":{"label":"Teaching source","pid":"example-source"}}}]}}
```

```json
{"message_id":32,"message_type":"set_ipt_configurations","data":{"sender_config_errors":[],"receiver_config_errors":[]}}
```

The parser checks required session lines, advertised media type, destination,
UDP, payload, codec/clock/channels and optional source-filter agreement, even
when format attributes are absent. Supplied supported attributes must agree.
Accepted line endings normalize to CRLF. This is a bounded subset, not full RFC
SDP or ST 2110 validation.

| SDP form | Accepted subset | Explicit limits |
| --- | --- | --- |
| `rx-1` video | `MP2T/90000` (static 33 or dynamic 96–127), or `H264/90000` / `H265/90000` (dynamic 96–127) | Payload 33 may omit rtpmap; other payloads require it; no additional video/audio attributes requiring fmtp interpretation |
| `rx-audio` audio | L16/L24, clocks 44100/48000/96000, 1–64 channels | Dynamic payload 96–127; static 10/11 only for L16/44100 stereo/mono; frame_size/link_offset unsupported with SDP |
| Shared syntax | One media and connection line; optional `mid` and one matching inclusive source-filter | Unknown SDP lines/attributes, fmtp, raw video, groups, multiple media, inline keys and crypto rejected |

Receiver SDP combined with spare IP state or SRT is rejected. Those configurations
can be modeled without SDP. The supported sender H.264/H.265 SDP is also outside
this receiver subset; no universal sender-to-receiver SDP round-trip is claimed.
`source_meta` is ignored, not secret-logged.

### Check, drift, repair and disable

```json
{"message_id":33,"message_type":"check_ipt_configuration","data":{"module_id":"module-1","config":{"id":"tx-1","sub_index":null,"transceiver_type":"sender","enabled_config":{"main_ip_destination":{"udp_port":5004,"address":"239.1.1.1","vlan":null,"network_interface":{"module_id":"module-1","port_id":"net-main"}},"spare_ip_destination":null,"format_info":{"video_codec":{"codec":"H.264","entropy_encoding":"CABAC","gop_struct":"IPB","gop_size":12},"attributes":{"rtp_payload_type":111}},"fec":null,"streaming":{},"resource_partner":null,"srt":null}},"set_again":false}}
```

```json
{"message_id":33,"message_type":"check_ipt_configuration","data":true}
```

After `simctl drift` removes that state, the same desired configuration with a
new request ID returns false. With `set_again: true`, it applies and rereads;
true means observed agreement. Failed apply/readback is a correlated `error`.
The comparison uses normalized supported domain state, not the original JSON.

```json
{"message_id":34,"message_type":"set_ipt_configurations","data":{"module_id":"module-1","sender_configs":[{"id":"tx-1","sub_index":null,"transceiver_type":"sender","enabled_config":null}],"receiver_configs":[{"id":"rx-1","sub_index":null,"transceiver_type":"receiver","enabled_config":null}]}}
```

```json
{"message_id":34,"message_type":"set_ipt_configurations","data":{"sender_config_errors":[],"receiver_config_errors":[]}}
```

```json
{"message_id":35,"message_type":"get_sender_sdp","data":{"module_id":"module-1","port_id":"tx-1"}}
```

```json
{"message_id":35,"message_type":"get_sender_sdp","data":null}
```

### Partial failure and advanced forms

```json
{"message_id":36,"message_type":"set_ipt_configurations","data":{"module_id":"module-1","sender_configs":[{"id":"tx-1","transceiver_type":"sender","enabled_config":null},{"id":"missing","transceiver_type":"sender","enabled_config":null}],"receiver_configs":[]}}
```

```json
{"message_id":36,"message_type":"set_ipt_configurations","data":{"sender_config_errors":[{"id":"missing","sub_index":null,"error":"Unknown parameter or resource"}],"receiver_config_errors":[]}}
```

An absent error item means success for that identity. Duplicate `(id, sub_index)`
entries in a direction are ignored after the first. Malformed item identity,
unknown module or more than 256 configurations causes a whole-request error.
A timeout can leave earlier items applied; batches do not provide rollback.

| Variant | Current modeled behavior | Limit |
| --- | --- | --- |
| Main/spare paths | Optional spare object; both interfaces must be advertised choices | No ST 2022-7 packets or failover engine |
| Unicast/multicast | IP addresses parsed; nonzero UDP; VLAN 1–4094 or null | No socket carrying media is opened |
| Streaming | Eight-bit QoS string, packet length 188/204, positive packet count/TTL, nonnegative rates | Control fields only |
| FEC | Positive length; null depth or positive matrix depth; skew; overhead 0–100 | No FEC calculation |
| SRT | Caller/listener, latency, overhead 0–100, optional AES128/192/256 key | Rejects multicast; no SRT engine; local key bound is not an SRT standard |
| Resource partner | Receiver reference permitted by the advertised `rx-tx` link | `tx-tx` selection semantics unresolved |
| Multi-vertex | Separate `(module, direction, id, sub_index)` state; null or 1–64 | Backend multiplicity must be commissioned separately |

For every documented format enum, metadata default, missing variant and test
disposition, use [COVERAGE.md](COVERAGE.md). In particular, do not invent values
for `main_interface_ip_overrides` or `spare_interface_ip_overrides`: the supplied
reference describes precedence but not their concrete non-null wire shape.
